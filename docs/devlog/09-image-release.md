# Phase 2 — GitOps and CI/CD

## Task 9 — Image Release to GHCR

### What was done

Created `.github/workflows/release.yml` for automated publishing of Docker images to **GHCR** (GitHub Container Registry) on semver tag push.

### Release Workflow

**Trigger**: `push` with semver tags (`v*.*.*`)

**What happens**:
1. GitHub Actions builds the Docker image using the existing `Dockerfile`
2. Image is pushed to `ghcr.io/Yash-Singh/KubeForge` with tags:
   - `v0.1.0` (full semver from git tag)
   - `0.1` (major.minor)
   - `latest` (convenience tag, for local dev only)
3. `docker/metadata-action` generates the tag scheme
4. Image is immutable and pinned to the git tag

### Image Strategy (per `specs/06-gitops-cicd.md`)

| Rule | Detail |
|---|---|
| **Default registry** | `GHCR` (`ghcr.io/Yash-Singh/KubeForge`) |
| **Tagging** | Immutable release versions only (`v0.1.0`, `v0.2.0`, etc.) |
| `latest` | Convenience tag only; must never be the deployment source for reproducible releases |
| **Provenance** | Signed or provenance-attested releases deferred until tooling is stable |
| **CDR changes** | Require explicit compatibility review before promoting |

### Release Process

```bash
# Step 1: Update version if needed (values.yaml already has v0.1.0)
git commit -am "release: bump to v0.2.0" && git push

# Step 2: Create and push semver tag
git tag v0.2.0 && git push --tags
```

**Automated by `release.yml`**:
- Builds image → pushes to GHCR
- Argo CD detects Git change → auto-syncs → new image pulled

### CI Workflow Integration

The `release.yml` job is separate from `test.yml`:
- `test.yml` — runs on every PR/push: format, lint, unit tests, envtest, manifests, CRD validation, helm, security scan
- `release.yml` — runs only on tag push: builds/publishes to GHCR

### Verification

- `release.yml` triggers on `git tag v0.1.0 && git push --tags`
- Image appears at `ghcr.io/Yash-Singh/KubeForge:v0.1.0`
- `helm template` renders correctly with `image.tag: v0.1.0`
- Argo CD Application syncs automatically after tag push

### Notes

- `latest` tag is generated by `docker/metadata-action` but **not** used as a deployment source per spec
- The workflow uses `docker/login-action@v3` with `secrets.GITHUB_TOKEN` (requires `packages: write` permission)
- No additional tools needed — GitHub Actions handles the full build/publish cycle
- Provenance/signing is deferred per spec ("when the tooling is stable enough to maintain")
